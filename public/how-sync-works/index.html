How shared drawings stay in sync

Everyone in a room draws on their own copy of the drawing, at the same time, with no locks. This page follows one box through the app to show how every copy ends up the same, using the real data shapes and messages.

1. Every editor has its own copy

In a shared room, each open tab holds the whole drawing, and so does the collab server. When you draw, your copy changes immediately, before anyone else hears about it. The edit is then sent to the server, which passes it on.

That raises the question this page answers: when two copies disagree, which one is right? The app needs an answer that every copy works out on its own, without asking anyone, and that comes out the same everywhere. That makes the drawing a CRDT (conflict-free replicated data type): copies that have seen the same edits are identical, whatever order the edits arrived in.

2. One register per element

The drawing is a map from element id to element. Each entry is a register: it holds one value, the latest version of that element. Two fields order the versions, and everything else is the value. This is a real rectangle, as the server held it during a test run:

  "index": "a0",
  "groupIds": [], "frameId": null, "boundElements": null,
  "seed": 1393476906, "updated": 1795375595057,
  "link": null, "locked": false
}

Key: id picks the register. Ordering: version counts the edits made to this element; versionNonce is a random number drawn at every edit. Value: everything else, and it travels as one piece. Two fields in the value look like they might matter, but neither decides a merge: index sets the stacking order between elements, and updated is a wall-clock timestamp.

The same map lives in three places, in three forms:

In each tab

The Excalidraw scene: an array of elements, deleted ones included.

On the server

Room.elements: a Map<string, SyncedElement> per open room.

In Postgres

One room_elements row per register: version, nonce, and the element as JSON.

The server only reads the ordering fields. It passes the rest through untouched (shared/protocol.ts):

type SyncedElement = {
  id: string;
  version: number;
  versionNonce: number;
  [key: string]: unknown;   // the value: whatever Excalidraw put there
};

3. The rule: one function decides

When a copy of an element arrives, the receiver compares it with the copy it already has. The server, every tab and the Postgres save all use this same comparison:

function wins(incoming, current) {
  if (!current) return true;                       // new element
  if (incoming.version !== current.version)
    return incoming.version > current.version;     // more edits wins
  return incoming.versionNonce < current.versionNonce; // tie: lower nonce wins
}

The rule only looks at the data, never at who sent it or when it arrived. So two copies that see the same pair of versions always keep the same one. That's what makes arrival order irrelevant.

5. Two people, one box, same moment

Alice drags the box while Bob recolours it. Both start from version 1, so both produce a version 2. Pick which edit reaches the server first. The ending is the same either way.

Bob's colour survives and Alice's move is lost entirely. A register holds a whole element, so the merge picks one complete copy and never combines fields from two. Field-level CRDTs such as Yjs would keep both changes, at the cost of more bookkeeping.

6. More edits beat later edits

version is an edit counter, not a clock. Here Bob edits while offline, five minutes after Alice, but she made more edits.

7. Deleting keeps a marker

A delete is an edit like any other: it sets isDeleted: true and bumps the version. The register stays in every copy and in Postgres. If it were removed, an older edit arriving late would look new and bring the box back.

8. What a tab sends: the synced record

A tab makes two different comparisons. When a copy arrives, it compares it with its own to decide what to show. When the user edits, it must decide what to send, but nothing has arrived to compare against. So each tab keeps a second map, the synced record: the newest version of each element the server is known to have. It sends an element only when the scene's copy wins against the record.

The record must hold copies. Excalidraw applies some edits in place: a drag bumps version and moves x on the same object. An earlier version of the editor stored the scene's own objects, so a drag changed the record too, and the drag was never sent. These are real values from reproducing that bug. The fix is in pull request #4.

9. Reconnecting

A tab that loses its connection keeps drawing. When it reconnects, the server sends an init message with its whole scene. The tab clears its synced record and refills it from that message, so the record says exactly what the server has. Then every local edit that beats it gets sent.

10. Saving: the same rule in SQL

While anyone is connected, the server keeps the room in memory and relays edits immediately. Edits that won are collected and written to Postgres 500 ms later, in one statement per batch. A register is one row:

create table room_elements (
  room_id text not null references rooms (id) on delete cascade,
  id text not null,
  version bigint not null,
  version_nonce bigint not null,
  data jsonb not null,          -- the whole element
  primary key (room_id, id)
);

The save is an upsert whose where clause is wins() written in SQL. A slow save can therefore never overwrite a newer row saved in between:

insert into room_elements (room_id, id, version, version_nonce, data) ...
on conflict (room_id, id) do update
  set version = excluded.version, version_nonce = excluded.version_nonce, data = excluded.data
  where excluded.version > room_elements.version
     or (excluded.version = room_elements.version
         and excluded.version_nonce < room_elements.version_nonce)

Cursors take a different path: they're relayed to the others and never stored. Images are stored per room under an id that is a hash of their content, and sent only to a tab that lacks one.

Recap

  • The drawing is a map of registers, one per element id. Each register holds one whole element.
  • One rule, wins(), picks between two copies: the higher version, then the lower random versionNonce. It depends only on the data, so every copy picks the same winner in any order.
  • Every copy runs the rule: the server, each tab, and the Postgres save. The server is just one more copy.
  • version counts edits; it isn't a clock. Deletes are markers that stay.
  • Each tab keeps a synced record of what the server has, made of copies, and sends only what beats it. A reconnect rebuilds the record from the server's real state.
  • The cost: when two people change the same element at once, one whole edit is dropped, and nobody is told.
